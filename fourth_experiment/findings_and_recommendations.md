# Находки и рекомендации — эксперимент 4: Hermes Agent + llama.cpp

Синтез по `acceptance_criteria.md` в этой же директории. Полный сетап/баги инфраструктуры —
память `project_fourth_experiment_hermes_llamacpp_setup` (не дублируется здесь).

## Итог одной строкой

`Qwen3-Coder-30B-A3B-Instruct` (Q3_K_M) через Hermes Agent + llama.cpp (bare-metal, GPU) проходит
golden-set задачу A/C **10/10** — после исправления трёх конфаундов, ни один из которых не был
про способность модели к tool-calling как таковую.

## Три найденных конфаунда — ни один не про модель

### 1. `HERMES_WRITE_SAFE_ROOT` — write-sandbox блокировал сам рабочий каталог

Официальный docker-образ Hermes сам выставляет `HERMES_WRITE_SAFE_ROOT=/opt/data` — запись за
пределы этого корня хард-блокируется, без approval-промпта. Рабочий каталог задачи (`/workspace`)
был вне этого корня — даже корректная попытка отредактировать `script.go` была бы физически
невозможна. Исправлено: `HERMES_WRITE_SAFE_ROOT=/workspace:/opt/data`. Задокументировано, что
именно этот механизм отвечает за фразу `Write denied: ... is outside HERMES_WRITE_SAFE_ROOT`,
которую видели в первых прогонах.

### 2. Контаминация через общее хранилище скиллов

Первый (сбойный) прогон не просто спутал задачу — модель реально **создала и сохранила**
`SKILL.md` в `/opt/data/skills/hermes-chat-name-flag/` с описанием, почти дословно совпадающим
с промптом задачи. Поскольку `/opt/data` персистентен, этот файл заражал все последующие прогоны
через skill-discovery на старте сессии — самоусиливающийся цикл. Вывод: **при любом повторном
использовании одного и того же профиля/`/opt/data` для серии независимых прогонов проверять и
чистить `skills/`, а лучше — использовать одноразовый/чистый профиль для eval'ов**, не то же
хранилище, что для боевой работы.

### 3. Системный промпт Hermes vs формулировка golden-set-задачи — self-reference confound

Самый интересный из трёх. 5/5 прогонов подряд (даже без skill-контаминации) модель трактовала
"Добавь флаг --name" как feature-реквест к **самому Hermes**, а не к файлу пользователя — прямое
следствие системного промпта Hermes ("When the user needs help with Hermes itself — configuring,
using, extending... load the `hermes-agent` skill"). Формулировка задачи A спроектирована в
`first_experiment` под opencode, у которого такого self-referential фрейминга нет — коллизия
специфична для Hermes, не воспроизводится на других харнессах с тем же промптом.

**Фикс — `workspace/AGENTS.md`** (штатный, задокументированный механизм project-level правил,
auto-injection по умолчанию, `--ignore-rules` отключает) с явным "ты работаешь над кодом в этой
директории, не над самим Hermes". Сработало со следующего же прогона.

**Практический вывод для любого будущего использования Hermes на generic coding-задачах**:
если формулировка задачи звучит как feature-реквест к CLI/агенту в общем виде ("добавь флаг",
"добавь команду", "настрой X") — стоит превентивно класть `AGENTS.md`/`.hermes.md` с явным
"это про код пользователя, не про Hermes", а не ждать, пока это всплывёт как баг.

## Побочный конфаунд, тоже не про модель — замусоренный `workspace/`

После фикса #3 один прогон ушёл в правку `tui_example.py` вместо `script.go` — за четыре
эксперимента `workspace/` накопил десятки посторонних файлов, и промпт задачи A никогда не
называл файл явно (полагался на то, что `script.go` — единственный подходящий кандидат в чистой
директории, как было при исходном проектировании задачи). Фикс — изоляция `script.go` в чистую
`workspace/fourth_experiment_task_a/` + `hermes chat --in <dir>` (штатный флаг, не меняет промпт).
После этого — 8/8 подряд без единого промаха по файлу.

**Вывод, применимый к будущим экспериментам**: golden-set задачи, спроектированные под "чистый
workspace", деградируют по мере накопления общих фикстур между экспериментами. Для новых раундов
сравнения — заводить изолированную поддиректорию на кандидата/раунд, не полагаться на то, что
общий `workspace/` останется однозначным.

## Находка, отдельно ценная для темы harness-верификации (`project_opencode_harness_verification`)

В **4 из 8** валидных PASS-прогонов текстовое саммари модели было прямо неточным или вводящим в
заблуждение ("replaced the original Go script with a Python implementation", "Created a Python
script (script.py)") — при этом сам `script.go` во всех случаях был отредактирован корректно.
Классический паттерн "саммари ≠ факт", который весь `first_experiment` пытался ловить внешним
харнесс-гейтом (`no_diff_markers_plugin.js`/`verify_gate_plugin.js`) для opencode.

**У Hermes это уже встроено** — file-mutation verifier (`display.file_mutation_verifier`,
включён по умолчанию) поймал именно этот класс проблемы на невалидных прогонах (когда правки
реально не было): `⚠️ File-mutation verifier: N file(s) were NOT modified this turn despite any
wording above that may suggest otherwise`. Не сработал ложноположительно ни разу — когда правка
реально была (пусть и описана неточно), предупреждения не было. Прямая параллель тому, что
пользователь пытался построить вручную для opencode в первом эксперименте — здесь это часть
продукта.

**Практический вывод**: при автоматизированной оценке Hermes-based агентов — не парсить текстовое
саммари как признак успеха вообще, полагаться (а) на объективный внешний verifier (как в этом
эксперименте — `go build`/`go run`) и (б) на встроенный file-mutation verifier как дополнительный,
более дешёвый сигнал прямо в выводе сессии.

## Остальной golden-set (B, D, E, F, G) — по одному прогону

Полный разбор — `acceptance_criteria.md`, раздел "Остальные задачи golden-set". Коротко:

| Задача | Результат |
|---|---|
| B (многофайловая правка) | **FAIL** — частичная реализация уверенно доложена как полная |
| D (verify-retry на реальном баге) | **PASS** — диагноз и фикс точные |
| E (self-critique, "не трогай X") | **FAIL** — прямое нарушение запрета |
| F (неоднозначная, без эталона) | защита работает, найден реальный баг в error-path |
| G (поиск/делегирование) | **PASS** — верный ответ, эффективный поиск (3 tool-call) |

**Смешанная картина 2 PASS / 2 FAIL / 1 без эталона — важная поправка к однозначному 10/10 на
задаче A.** Кандидат надёжен на простой, однозначной, самодостаточной задаче (A/C), но проваливает
и многофайловую координацию (B), и явный запрет (E) — оба раза не из-за неспособности к
tool-calling (файлы правились, компилировались), а из-за **неполноты реализации при уверенном
заявлении об успехе (B)** и **игнорирования явного ограничения (E)**. Это ровно те классы
проблем ("диагноз ≠ фикс", self-critique), которые `first_experiment` пытался закрыть
промпт-инженерией для opencode — здесь видно, что они воспроизводятся и на другом
харнессе/бэкенде/модели, то есть не специфичны для opencode+ollama.

**Задача B — отдельно ценная методологическая находка**: встроенный file-mutation verifier
Hermes поймал ровно один дублирующий/избыточный сбойный `patch`, но не поймал сам факт неполноты
(диспетчеризация и чтение тела POST остались нетронутыми, хотя другие части файла — реально
менялись). Verifier различает "файл тронут / не тронут", не "тронут ПОЛНОСТЬЮ корректно" — этот
уровень детализации по-прежнему требует внешней функциональной проверки.

## Метрики (10 валидных прогонов)

- **Success rate**: 10/10 (100%), выше оговорённого порога 8/10.
- **Malformed tool-calls**: 0/10.
- **Empty-response / silent-exit**: 0/10.
- **Latency**: ~1 минута на прогон (GPU, prompt+generation), не измерялась с точностью до секунд
  (не было целью этого раунда — фокус на success rate и классификации провалов).
- **Точность текстового саммари**: 4/10 прогонов дали неточное/вводящее в заблуждение саммари при
  фактически корректной правке — отдельная метрика, не влияющая на success (объективная проверка
  всегда была решающей), но релевантная для доверия отчётам агента "на слово".

## Сравнение с предыдущими экспериментами

`second_experiment` (Ollama, 7 моделей) — 0/7 кандидатов прошли даже smoke-test. `third_experiment`
(vLLM) — PLANNED, не прогонялся. Этот, четвёртый — первый эксперимент серии, где кандидат реально
прошёл golden-set N=10 с высоким success rate. Разница объясняется совокупностью факторов, не
одним: (а) бэкенд/харнесс с задокументированной моделеспецифичной поддержкой tool-calling
(llama.cpp + официально "нативный" tool-format для Qwen-семейства, в отличие от общего Go-шаблона
Ollama), (б) достаточный размер модели (30B-A3B, не ≤20B/7B кандидаты предыдущих раундов — прямое
эмпирическое подтверждение гипотезы, впервые высказанной как предположение в
`second_experiment/findings_and_recommendations.md`), (в) исправленные харнесс-специфичные
конфаунды выше, без которых даже полностью способный кандидат показал бы 0%.

## Рекомендации

1. **`Qwen3-Coder-30B-A3B-Instruct` (Q3_K_M) через Hermes+llama.cpp — рабочий, но не безупречный
   кандидат**: 10/10 на простой самодостаточной задаче (A/C), но 2 FAIL из 5 на более сложных
   (многофайловая координация — B, явный запрет — E). Не дисквалифицирует кандидата (профиль
   ошибок — про полноту/самоконтроль, не про поломанный tool-calling), но не round up до "готов
   для сложных задач без присмотра" по одному раунду N=1 на B/D/E/F/G.
2. **Три инфраструктурных фикса — воспроизводить при любом новом развёртывании этого стека**:
   `HERMES_WRITE_SAFE_ROOT` под реальный workspace, чистый/изолированный `/opt/data` (или отдельный
   профиль) под eval-серии, `AGENTS.md` в workspace для generic coding-промптов.
3. **Не доверять текстовому саммари Hermes без верификации** — 40% неточных саммари даже среди
   успешных прогонов; встроенный file-mutation verifier — минимальный бесплатный сигнал, но не
   замена объективной внешней проверки.
4. Если продолжать сравнение — стоит прогнать эту же задачу на **исходном промпте без
   `AGENTS.md`-фикса, но с другой, менее CLI-похожей формулировкой** отдельным заходом, чтобы
   отделить "промпт похож на CLI-фичреквест" от "Hermes всегда путает себя с проектом" — этот
   раунд проверял только конкретно задачу A, обобщение на другие формулировки не проверялось.
