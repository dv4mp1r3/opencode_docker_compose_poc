**Контекст**: `qwen2.5-coder:14b` без констрейнта — подтверждённо 100% malformed tool-calls

главный незакрытый долг первого эксперимента, который стоит закрыть здесь.

**Открытый технический вопрос, не решённый на момент планирования**: как именно прокинуть

факт, что openai-compatible эндпоинт и/или provider-адаптер opencode прокидывают эквивалентный
параметр.

**Промежуточный шаг перед исследованием констрейнта — эмпирическая проверка без него** (быстрее,
чем гадать про параметр): в `config/opencode.jsonc` `"tools": false` → `"tools": true` для
`qwen2.5-coder:14b` (без какого-либо констрейнта), smoke-test.

## Гипотеза #1 (headless vs интерактивный TUI) — проверена, ОПРОВЕРГНУТА

Метод: реальный интерактивный TUI (`docker compose exec -it opencode opencode`, то же, что
запускает `make code`) продиктован через `expect` (эмуляция настоящего псевдотерминала — не флаг
`opencode run -i`, который на проверку не меняет список доступных тулов и остаётся, по сути,
headless-режимом с другим рендером). Технически непросто: TUI использует полноэкранный
truecolor-протокол с посимвольной адресацией курсора (похоже на кастомный рендерер, судя по
служебным escape-последовательностям `opentui-notifications`) — сырой лог `expect` нечитаем
напрямую, пришлось вытаскивать результат через `make log get` по ID сессии, которую TUI создаёт
сам (заголовок автогенерируется из текста задачи).

**Результат (`ses_fd95da2f6ffewKiNiQsARhYGdp`, `gpt-oss:20b`, `think: medium`, тот же промпт A):**
- Подтверждённое отличие от headless: **`question` присутствует в списке доступных тулов**
  (`bash, edit, glob, grep, invalid, lsp, question, read, skill, task, todowrite, webfetch, write`)
  — в headless его нет.
- Но: **тот же класс галлюцинации** — первый вызов инструмента снова `repo_browser.glob`
  (несуществующий тул, тот же паттерн, что в 3 из 4 headless-прогонов на gpt-oss). Модель
  самовосстановилась и вызвала реальный `glob("**/*")` — но на этом успехи закончились: ответ
  завершился `finish: "stop"` с текстом "Sure thing! How can I assist you..." — **тот же паттерн
  потери нити задачи после ошибки**, что систематически наблюдался в headless. `script.go` не
  тронут.

**Вывод: гипотеза #1 отклонена.** Наличие `question` в наборе тулов — реальное отличие
интерактивного режима, но оно не является причиной провала: тот же класс галлюцинации
несуществующих имён тулов и та же потеря нити задачи после ошибки воспроизводится и в
полноценном TUI. Проблема не в headless-режиме как таковом.

**Практическое ограничение метода**: автоматизация TUI через `expect` технически хрупкая и дорогая
(зависимость от псевдотерминала, риск зависших процессов при неверной последовательности
`sleep`/`expect`/`close` — один диагностический прогон уже завис на `wait` и потребовал ручного
`kill`). Для одного контрольного замера это оправдано, для полноценного N=10 по каждому кандидату
в TUI — нет, разумнее держаться headless как основного метода дальше, раз он даёт тот же сигнал.

## Гипотеза #3 (задача A не называет файл явно) — проверена, ОПРОВЕРГНУТА

Метод: та же задача A, headless, `gpt-oss:20b`@medium (тот же кандидат, что и в раунде 1, для
чистоты сравнения — единственная переменная, которая меняется, это формулировка промпта), но с
явно указанным путём файла. Было: *"Добавь флаг --name..."* (без упоминания файла). Стало:
*"В файле script.go добавь флаг --name..."*.

| # | Session ID | Результат | Причина |
|---|---|---|---|
| 1 | `ses_fd76192f5ffeIzExU0DwcBhytA` | **FAIL** | Галлюцинация `container.exec` на первом же шаге — до того, как модель успела бы вообще прочитать/использовать указанный путь. Дальше — "чем могу помочь" |

реакция на конкретную формулировку задачи, а нечто более общее в том, как эта модель начинает
формировать самый первый tool-call в этой связке.

## Статус эксперимента на 2026-08-22 (конец раунда 1 + гипотезы #1, #3)

количественно — тот же итог: 0% success rate на simplest задаче golden-set за все протестированные
прогоны.

**Критически важная находка, подтверждающая кросс-модельный паттерн**: `explore` — это не случайное

Это уже **третье независимое подтверждение** одной и той же гипотезы за эксперимент 2:
- `gpt-oss:20b` → `container.exec`, `repo_browser.*`
- `devstral-small-2:24b` → делегирование в `task(subagent_type="general")` с "General Agent" —

- `qwen3-coder:30b` → явный `subagent_type=explore`, имя параметра `prompt`/`description` — вплоть
  до структуры аргументов, совпадающей с реальным API инструмента `Task` в Claude Code

Это не совпадение три раза подряд на трёх разных архитектурах/поставщиках моделей (OpenAI gpt-oss,
Mistral devstral, Alibaba qwen3-coder). Наиболее вероятное объяснение: все три модели в процессе
дообучения на синтетических agentic/tool-calling датасетах видели данные, сгенерированные или
размеченные с использованием Claude Code (сейчас один из самых распространённых источников
публичных агентных трасс для дистилляции/файнтюнинга) — и стохастически "вспоминают" именно этот
тулсет, когда сталкиваются с задачей "исследуй код, потом отредактируй", независимо от того, какой
реальный тулсет им передан в системном промпте текущего запуска.

**Практическое следствие**: если гипотеза верна, для будущих раундов было бы полезно явно
"прописать" в `agent_prompt.txt` короткое явное опровержение самых частых конкретных
галлюцинированных имён (`explore`, `general`, `container.exec`) — не как общее "не выдумывай
тулы" (уже есть неявно через корректный список), а как точечный "если тебе хочется вызвать
`explore`/`Task(subagent_type=...)` в стиле другого агента — здесь это `glob`+`read` напрямую или
`task(subagent_type="scout")`". Проверено ниже — не помогло.

### Уточнение источника галлюцинаций (2026-08-22) — это НЕ путаница с Claude Code

Первоначальная гипотеза (три модели "вспоминают" тулсет Claude Code из-за его распространённости в
синтетических agentic-датасетах) была слишком поспешной — проверена по существу через WebSearch/
WebFetch на официальные источники, и опровергнута в пользу значительно более точного и куда более
практически значимого объяснения: **каждая модель галлюцинирует названия тулов ИЗ ХАРНЕССА СВОЕГО
ЖЕ ВЕНДОРА**, под который она официально документирована/файнтюнена — не из стороннего продукта.

- **`gpt-oss:20b` → `container.exec`, `repo_browser.*`, `apply_patch`**: подтверждено дословно в
  официальном репозитории [`openai/gpt-oss`](https://github.com/openai/gpt-oss) — это
  задокументированные **"in-distribution tools"** модели: *"The model's in-distribution tools
  include container.exec, repo_browser and apply_patch... To achieve proper performance, you
  should provide the model's in-distribution tools ... and implement a native Harmony harness."*
  Модель делает ровно то, для чего её обучали — не путается со сторонним продуктом, а honestly
  ожидает интерфейс, который OpenAI сама прямо рекомендует харнесс-разработчикам реализовать.
  Никакого способа адаптации через system prompt (переопределение имён тулов) в документации не
  описано — деградация при несовпадении интерфейса не документирована вообще, то есть мы попали
  ровно в тот пробел, который авторы не проговорили.
- **`qwen3-coder:30b` → `explore`, `general-purpose`**: подтверждено в официальной документации
  [Qwen Code](https://qwenlm.github.io/qwen-code-docs/en/users/features/sub-agents/) — собственного
  CLI-харнесса Alibaba для их же coder-моделей. Это ровно два встроенных subagent-типа этого
  инструмента (`Explore` — read-only исследование кода; `general-purpose` — дефолт при отсутствии
  `subagent_type`). Опенкодовский `task(subagent_type="scout")` использует другое имя — модель,
  видимо, дообучена/протестирована именно против Qwen Code и не видела альтернативных схем.
- **`devstral-small-2:24b`**: не найдено прямого документального подтверждения конкретно имени
  `"General Agent"`/`subagent_type="general"` у официально рекомендованного харнесса Mistral
  ([OpenHands](https://www.openhands.dev/blog/devstral-a-new-state-of-the-art-open-model-for-coding-agents),
  альтернатива — SWE-Agent) — этот пункт остаётся не до конца проверенным, в отличие от двух
  других. Но найдена **отдельная, независимо важная находка**: для Devstral в его же официально
  рекомендованном стеке (vLLM + OpenHands) прямо требуется флаг `--tool-call-parser mistral` —
  *"omitting it causes malformed function call output that breaks the OpenHands agent loop"*
  ([источник](https://www.spheron.network/blog/deploy-openhands-gpu-cloud/)). Ollama (которую мы
  используем) не имеет специализированного per-модельного tool-call парсера уровня vLLM — только
  общий Go-шаблон на тег модели. Это правдоподобная, отдельная от "путаницы с именами" причина
  замеченных у нас schema-ошибок (`Missing key ["oldString"]`/`["filePath"]`) — не поведенческая
  путаница модели, а протокольное рассогласование парсера.

**Почему это меняет вывод, а не просто уточняет его**: если источник — не "модель спутала два
продукта" (что теоретически лечится/смягчается длинным описанием в промпте, хоть мы и проверили,
что не лечится), а "модель обучена под конкретный, задокументированный интерфейс, которого Ollama +
opencode ей не предоставляют" — то промпт-инженерия в принципе не тот уровень, на котором лежит
решение. Более обоснованные направления:
1. **Ollama, вероятно, структурно не подходящий бэкенд для этих конкретных open-weight моделей** —
   не потому что Ollama "плохая", а потому что каждая из этих моделей официально рассчитана на
   конкретный tool-call parser/харнесс (Harmony-native harness для gpt-oss, `--tool-call-parser
   mistral` для Devstral, Qwen Code для Qwen3-Coder), которого Ollama не реализует специфично под
   каждую модель.
2. Проверить эмпирически (не гадая) — даёт ли vLLM с корректным `--tool-call-parser` для Devstral
   на этом же хосте иную картину, чем Ollama. Это отдельный, ранее не рассматривавшийся кандидат
   на инфраструктурную переменную (бэкенд инференса), а не просто "другая модель".
3. Уточнение по ходу переписки 2026-08-22: для `qwen3-coder:30b` путь "просто сменить парсер"
   в vLLM оказался даже чище, чем для Devstral — `Qwen/Qwen3-Coder-30B-A3B-Instruct` прямо в
   официальном списке поддерживаемых моделей vLLM с однозначным парсером `qwen3_xml`, без
   известных открытых issue уровня Devstral. Для `gpt-oss` аналогичного простого пути нет —
   его контракт "native Harmony harness" качественно сложнее одного флага.
