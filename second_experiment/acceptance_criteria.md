# Критерии приёмки — эксперимент 2: сравнение модель/бэкенд для agentic tool-calling

Начато 2026-08-21/22. Не код проекта — рабочий артефакт планирования и учёта прогонов, парный
`first_experiment/acceptance_criteria.md` по формату. Обновляется по ходу — статус каждого
кандидата и предварительные результаты фиксируются здесь же, синтез — в
`findings_and_recommendations.md` в этой же директории.

## Контекст и почему это отдельный эксперимент, а не продолжение первого

`first_experiment` (2026-08-10) сфокусирован на промпт/harness-инженерии (verify-retry,
self-critique, diff-маркеры) на фиксированной паре модель+бэкенд (`gpt-oss:20b` через Ollama).
Этот, второй эксперимент — про сам выбор модели/бэкенда, который до сих пор не проверялся тем же
методом, каким проверялось всё остальное: **объективным golden-set прогоном, а не анекдотом**.

Триггер: в текущей рабочей сессии (2026-08-20/21) на `gpt-oss:20b` последовательно найдены три
независимых бага, из них минимум один — неисправимый нашими средствами upstream-баг Ollama
(harmony-парсер роняет ответ модели молча, открытые issue
[ollama/ollama#11991](https://github.com/ollama/ollama/issues/11991),
[#11781](https://github.com/ollama/ollama/issues/11781),
[#12187](https://github.com/ollama/ollama/issues/12187), без подтверждённого фикса). Подробности
и хронология — см. `project_opencode_toolset_mismatch.md` в памяти проекта (не в репозитории).

При этом решение "заменить qwen2.5-coder:14b на gpt-oss:20b", зафиксированное в `plan.txt`
(корень репозитория) и в `first_experiment/findings_and_recommendations.md` §3.6, опиралось на:
- **подтверждённый** прямым `curl`-тестом факт: `qwen2.5-coder:14b` через Ollama в 100% случаев
  отдаёт сырой JSON вместо `tool_calls` (независимо от сложности схемы; баг специфичен именно
  для coder-версий Qwen2.5 + Ollama, не Qwen3-Coder — см. `plan.txt` строки 7-9);
- **непроверенную** гипотезу фикса — `first_experiment/acceptance_criteria.md` заводит под это
  отдельный пункт "п.3 constrained tool-calls", но `findings_and_recommendations.md` §1.2 прямо
  фиксирует: "Задачи п.3 ... сегодня не трогали вообще".

Вывод: у обоих кандидатов на сегодня есть подтверждённый, но разный failure mode, и ни один не
прогнан через N=10 сравнение. Переключение по одному новому анекдоту вместо другого — то, чего
явно хочет избежать пользователь (см. переписку 2026-08-21/22). Этот эксперимент — попытка
закрыть именно этот пробел.

## Новые ограничения сетапа (зафиксированы пользователем 2026-08-21)

- Тестирование переезжает на **внешний хост** (не Docker/Ollama из `docker-compose.yml` этого
  репозитория) — GPU там NVIDIA RTX 4070 Ti SUPER, **≤16GB VRAM** (по факту ~15.16 GiB usable,
  видно из лога ollama, присланного пользователем 2026-08-21: `CUDA0 (15946 MiB, 15161 MiB free)`).
- Кандидат обязан поддерживать tool calling (не обязательно нативно от разработчика модели —
  но обязательно рабочее в связке с используемым бэкендом, это и есть то, что мы измеряем).
- opencode по-прежнему запускается локально (в Docker этого репозитория) и обращается к внешней
  Ollama по сети через `OLLAMA_HOST` — то есть у меня (Claude) есть доступ к стороне opencode
  (конфиг, `make log get`, локальные логи `logs/opencode/opencode.log`), но **нет доступа** к
  самому внешнему хосту/Ollama и её логам — их придётся присылать вручную, как это уже делалось
  2026-08-21 при диагностике harmony-бага.

## Задачи (golden-set)

Переиспользуется без изменений из `first_experiment/acceptance_criteria.md`:
- **Задача A** (тривиальная точечная правка, `script.go`, флаг `--name`) — как разовый smoke-test
  перед полным прогоном на каждом кандидате (быстро отсеять кандидата, который не проходит даже
  тривиальный случай, не тратя N=10 сразу).
- **Задача C** (стабильность tool-calling, N=10 повторов задачи A) — основной сравнительный
  прогон, по каждому кандидату отдельно.

Формулировки — см. `first_experiment/acceptance_criteria.md`, не дублируются здесь намеренно
(единственный источник истины для текста промпта golden-set — тот файл).

## Метрики

Унаследованы из первого эксперимента:
- **success** — бинарно, по объективному проверяющему (`go build` / `go run --name=Ivan`
  печатает `Hello, Ivan!`) — не "на глаз".
- **malformed tool-calls** — доля прогонов, где модель вернула сырой JSON вместо `tool_calls`
  (исходная метрика п.3, специфична для протокольного уровня, не для harmony).
- **wall-clock latency**, **токены** (input/output/пик контекста), **число tool-вызовов**.

Новая метрика, добавленная по итогам находок 2026-08-20/21 (harmony-баг gpt-oss):
- **empty-response / silent-exit rate** — доля прогонов, где шаг ассистента завершается с
  `finish: "unknown"` (или иным нестандартным reason), 0 output-токенов, без tool-call и без
  текста, и опенкод завершает цикл (`"exiting loop"` в `logs/opencode/opencode.log`) без ответа
  пользователю. Отдельная метрика от malformed tool-calls: там модель ХОТЬ ЧТО-ТО возвращает
  (просто не в том формате), здесь — не возвращает ничего пригодного для показа пользователю.
  Источник находки — `ses_fded7bdddffecb5t8zznj29utR` (см. память
  `project_opencode_toolset_mismatch.md`).

## Процедура прогона (черновик, уточнить перед первым реальным прогоном)

1. Переключить активную модель в `config/opencode.jsonc` (`"model"` на верхнем уровне и/или через
   `OPENCODE_MODEL` в `docker-compose.yml`) на кандидата.
2. Прогнать задачу A один раз (smoke-test). Если FAIL по инфраструктурной причине (permission,
   allowlist, отсутствие тулчейна) — чинить инфраструктуру, не засчитывать как провал кандидата,
   перезапускать smoke-test.
3. Если smoke-test PASS — прогнать задачу C (10 повторов), после каждого прогона:
   - `make log get <id>` → зафиксировать в этом документе (таблица ниже) success/fail, причину,
     tool-calls, латентность;
   - при подозрении на harmony-класс сбоя (пустой ответ, `finish: unknown`) — запросить у
     пользователя синхронный фрагмент лога внешней Ollama за то же время (у меня нет доступа
     напрямую), сверить с `logs/opencode/opencode.log` этого репозитория по временной метке.
4. Заполнить сводную таблицу метрик по кандидату в `findings_and_recommendations.md`.

**Решено 2026-08-22**: прогоны инициирует Claude, headless, через
`docker compose exec -T opencode opencode run -m ollama/<модель> --title "<тег>" "<промпт>"`
(не интерактивный TUI). Оговорка про headless vs интерактивный TUI из первого эксперимента (обрыв
сессии на reject permission в headless) актуальна и здесь.

**Методологическая оговорка, всплывшая на первых же прогонах (2026-08-22)**: на `gpt-oss:20b`
(оба уровня `think`) в 3 из 4 headless-прогонов встретилась галлюцинация несуществующих тулов
`container.exec`/`repo_browser.*` — паттерн, ни разу не встречавшийся в предыдущих "боевых"
сессиях этого проекта (см. `project_opencode_toolset_mismatch.md`). Не исключено, что это
частично артефакт именно headless-режима (отличается набор доступных тулов — например, `question`
пропадает из списка, спросить не у кого) или просто нормальная стохастика модели, которая раньше
не попадалась на исследованных сессиях по случайности выборки. Полученные здесь результаты стоит
интерпретировать как "headless-нижняя граница устойчивости" (терминология из
`first_experiment/acceptance_criteria.md`), не как точную оценку опыта в интерактивном TUI.

## Регресс vs улучшение

Переиспользуется формулировка первого эксперимента: регресс — падение success rate, рост
malformed/empty-response rate относительно любого уже измеренного кандидата; улучшение — кандидат
проходит C стабильно (в идеале 10/10, приемлемо — явно оговорённый порог до начала прогона по
конкретному кандидату, не постфактum).

## Инфраструктурная правка по ходу раунда 2 (2026-08-22): `find *` в bash-allowlist

Первый smoke-прогон `devstral-small-2:24b` упёрся в `bash find ...` не из allowlist —
auto-reject в headless (тот же класс инфраструктурного провала, что уже документирован в
`first_experiment` для `sleep`/`pkill`/`true`/`false`). Добавлено `"find *": "allow"` в
`agent.auto.permission.bash` и `agent.bare.permission.bash` в `config/opencode.jsonc`. По
методологии первого эксперимента — инфраструктурные провалы не засчитываются кандидату,
прогон повторён после фикса.

## Диагностический артефакт в конфиге: агент `bare`

Добавлен в `config/opencode.jsonc` (`agent.bare`) 2026-08-22 для проверки гипотезы #2 (влияет ли
`agent_prompt.txt` на галлюцинацию несуществующих тулов) — primary-агент с теми же `permission`,
что у `auto`, но без поля `prompt` (наследует встроенный дефолт opencode вместо нашего текста).
Вызывается через `opencode run --agent bare`. Оставлен в конфиге после использования — не мешает
остальным агентам, может пригодиться для дальнейшей изоляции переменных на других кандидатах.
Результат проверки — см. `findings_and_recommendations.md`, раздел "Гипотеза #2".
