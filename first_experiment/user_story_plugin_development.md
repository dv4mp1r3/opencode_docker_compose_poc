# User story: harness-плагин обязательной функциональной верификации

## Зачем этот документ

Живой журнал решений по разработке plugin'а для opencode, который реализует обязательную
функциональную проверку на уровне harness'а — накапливается по ходу работы, чтобы не
восстанавливать историю решений из переписки заново на следующей итерации. Формат — только
дописывание (append-only): новые находки/решения добавляются в соответствующий раздел, старое
не переписывается (если решение отменяется — новая запись со ссылкой на то, что отменяет, а не
правка задним числом).

## Для какой фазы это делается и почему (контекст)

Фаза: реализация конкретной инженерной рекомендации из эксперимента по качеству локального
агента (`acceptance_criteria.md`, `findings_and_recommendations.md`, 2026-08-10) — раздел 3.1/3.4
находок.

**Почему harness, а не промпт**: golden-set эксперимент (Stage A/B/C по задаче D', RNFR/RNTO)
показал за три раунда, что усиление формулировки в `agent_prompt.txt` и правило post-verify
("диагноз ≠ фикс") — по отдельности и вместе — не устраняют главную проблему: модель либо не
проверяет своё изменение вовсе (рационализирует отказ прямо в reasoning), либо — хуже —
корректно диагностирует баг через функциональный тест, но заявляет об успехе, не убедившись,
что фикс реально применился ("ложный успех"). Это не наша уникальная находка: работа
["From Confident Closing to Silent Failure: Characterizing False Success in LLM Agents" (arXiv 2606.09863)](https://arxiv.org/abs/2606.09863)
называет это доминирующим классом отказа (75.8% провалов на AppWorld), не редким краевым
случаем.

**Практический вывод (зафиксирован в `findings_and_recommendations.md`, разделы 3.1/3.4)**:
верификация должна быть обязательным шагом пайплайна, не зависящим от решения модели —
гейт между "модель считает себя готовой" и "результат зафиксирован как выполненный", на
уровне harness'а (plugin opencode), а не очередная формулировка в промпте.

Более широкий пользовательский запрос, породивший эту фазу: *"добавить обязательную
функциональную проверку на уровне harness'а"*.

## 1. Подтверждённые факты об API плагина opencode (версия 1.18.16)

Все факты в этом разделе — не из документации "на слово", а либо подтверждены прямым
эмпирическим тестом внутри контейнера `opencode`, либо явно помечены как "из документации,
не перепроверено". Источник документации:
`https://raw.githubusercontent.com/anomalyco/opencode/dev/packages/web/src/content/docs/plugins.mdx`
(ветка `dev`, может опережать установленную версию 1.18.16 — отсюда и практика перепроверки).

### 1.1 Полный список хуков (из документации)

- Tool: `tool.execute.before`, `tool.execute.after` — сигнатура `async (input, output) => {}`
- Event (ОДИН общий ключ `"event"`, не отдельные ключи по имени): `session.created`,
  `session.idle`, `session.error`, `session.updated`, `session.compacted`, `session.deleted`,
  `session.diff`, `session.status`, `message.updated`, `message.part.updated`,
  `message.part.removed`, `message.removed`, `permission.asked`, `permission.replied`,
  `file.edited`, `file.watcher.updated`, `command.executed`, `todo.updated`, `shell.env`,
  `installation.updated`, `lsp.client.diagnostics`, `lsp.updated`, `server.connected`,
  `tui.*`, `experimental.session.compacting` — сигнатура `async ({ event }) => {}`, различать
  по `event.type`.
- Кастомный tool: `tool: { name: tool({...}) }` в возврате плагина, приоритет над встроенными
  при совпадении имени.
- Логирование: `client.app.log({ body: { service, level, message } })`.
- Контекст фабрики плагина: `async ({ project, client, $, directory, worktree }) => {...}` —
  `$` это Bun shell API, доступен прямой запуск команд из плагина.

### 1.2 Блокировка через throw — ПОДТВЕРЖДЕНО эмпирически, 2026-08-10

- `throw` в `tool.execute.before` **блокирует** вызов для `input.tool === "bash"` (первый тест)
  и для `input.tool === "write"` (второй тест) — в обоих случаях: действие физически не
  произошло (файл/эффект отсутствует), tool вернул `state.status = "error"`, модель получила
  ошибку как обычный провал tool-вызова и адекватно отреагировала (не заявила ложный успех).
  `edit` отдельно не тестировался, но это тот же типовой путь, что `write` — поведение разумно
  считать общим.
- Устаревшая заметка в `config/no_diff_markers_plugin.js` ("throw не блокирует, глушится
  движком") **не воспроизводится** на 1.18.16 для `bash`/`write`. Комментарий в файле стоит
  считать устаревшим для этого случая (сам плагин там намеренно использует мутацию `args`, а
  не throw — исторически, возможно, по другой причине или на другой версии; менять
  `no_diff_markers_plugin.js` сейчас не нужно, он и так рабочий).

### 1.3 Event-хуки — throw НЕ блокирует, ПОДТВЕРЖДЕНО эмпирически, 2026-08-10

- Throw в `event`-хуке (проверено на `message.part.updated` с финальным текстом и на
  `session.idle`) долетает до движка и печатается в лог как полный stack trace, но **не
  останавливает** ничего — финальный текст всё равно печатается пользователю, процесс не
  падает, exit code 0.
- Порядок событий перед печатью ответа: `message.part.updated`(финальный text, `time.end`
  проставлен) → `message.part.updated`(step-finish) → `message.updated`×2 →
  `session.status`(busy→idle) → `session.idle` → **только тогда** CLI печатает текст.
- **Следствие**: заблокировать сам текст финального ответа модели ("готово"/ложный успех)
  невозможно на этом API в принципе — не ограничение дизайна гейта, а ограничение платформы.
  Гейт может блокировать только tool-вызовы (действия), не факт того, что модель скажет.

### 1.4 sessionID и мутация output — ПОДТВЕРЖДЕНО эмпирически, 2026-08-10

- `input` в обоих tool-хуках содержит `sessionID`: форма `{tool, sessionID, callID, args?}`
  (`args` присутствует в `tool.execute.after`, отсутствует/пуст в `tool.execute.before` до
  того как его же смотришь через `output.args`). Значит состояние гейта можно корректно
  скоупить по сессии.
- Мутация `output` в `tool.execute.after` реально доходит до модели: проверено на `write` —
  мутировали `output.output`/`output.title`/`output.metadata.filepath`, добавленный маркер
  появился в `state.completed.output` того же `tool`-part в event-стриме, то есть в том виде,
  в каком результат уходит в историю разговора. **Инъекция результата авто-верификации прямо
  в вывод `edit`/`write` технически работает.**

### 1.5 Инфраструктурная находка: залипающий bind-mount на macOS

При быстрых правках `config/opencode.jsonc` с хоста контейнер иногда продолжает видеть старую
(рваную, обрезанную на случайной строке) версию файла даже после ожидания нескольких секунд —
похоже на кэширование bind-mount (virtiofs/gRPC-FUSE на Docker Desktop для macOS), не на
гонку: простое ожидание не помогает. Лечится `docker compose restart opencode`. Практика:
перед каждым прогоном с изменённым конфигом сверять `wc -l` файла изнутри контейнера с хостовым
значением; при расхождении сразу рестартовать контейнер, не тратить время на повторные попытки
подождать.

## 2. Дизайн гейта (текущая версия, 2026-08-10)

### 2.1 Модель состояния (per-session, в памяти плагина)

```
pendingVerification: boolean   // есть правка(и), не подтверждённые прогоном проверки
lastEditFiles: string[]        // какие файлы правились с последней успешной проверки
attemptsSinceEdit: number      // счётчик попыток верификации, cap = 3 (см. agent_prompt.txt)
```
Скоупится по `sessionID` (см. 1.4) — подтверждено, что он доступен в обоих tool-хуках.

### 2.2 Три точки хука

1. **`tool.execute.after` на `edit`/`write`** — не блокирует. Ставит `pendingVerification =
   true`, запоминает файл. Сам инициирует проверку через `$` (не дожидаясь решения модели —
   прямая реализация рекомендации 3.4 из `findings_and_recommendations.md`). Результат
   (PASS/FAIL + краткий вывод) дописывается в `output` (см. 1.4 — подтверждено, что долетает
   до модели). При PASS → `pendingVerification = false`.
2. **`tool.execute.before` на `edit`/`write`** — точка блокировки. Если
   `pendingVerification === true` — `throw` с внятным сообщением, что именно не подтверждено и
   что нужно сделать. Использует `throw` (подтверждённо блокирует, см. 1.2), не
   permission-механизм (тот в headless фатален при reject).
3. **Cap = 3** — при `attemptsSinceEdit >= 3` гейт перестаёт блокировать (пропускает дальше),
   но `pendingVerification` остаётся `true` и это должно быть видно в итоговом логе сессии как
   факт "осталось неподтверждённым" — не даёт молча потеряться в отчёте.

### 2.3 Почему блокировать именно "следующую правку"

Нацелено на реально наблюдавшийся дефект (Stage C, `findings_and_recommendations.md`), не на
гипотетический: модель внесла правку-диагноз, затем ещё правки поверх, где-то в процессе
`do_REST` слился в `do_RNTO` — обнаружилось через несколько шагов, когда контекст уже далеко
ушёл. Блокировка второй правки без верификации первой — это то самое место, где реальная порча
кода в прошлом эксперименте осталась незамеченной дольше всего; при гейте она бы всплыла сразу
после появления, с моделью, ещё помнящей контекст своей правки.

### 2.4 Честно про остаточный пробел

Гейт **не может** помешать модели соврать словами сразу после единственной правки, если она не
пытается сделать вторую (см. 1.3 — событие финального сообщения не блокируется в принципе).
Смягчается инъекцией результата авто-верификации прямо в `output` той же правки (2.2, шаг 1) —
модель видит FAILED в собственном контексте до того, как решит, что писать, но это не жёсткая
гарантия, только повышение вероятности, что модель не проигнорирует видимый факт.

## 3. Эвристика "что считается верификацией" — обсуждение

### 3.1 Рамка

Совпадение статической и функциональной проверки — разный уровень доверия, что подтверждено и
литературой, и нашими собственными экспериментами (`NameError` на `REPLY_350` не поймана
`py_compile`; `do_RNFR`/`do_RNTO` вне класса — синтаксически валидный Python, ловится только
исполнением).

### 3.2 Рассмотренные варианты

| # | Вариант | Обоснование "за" | Обоснование "против" / риск |
|---|---|---|---|
| 1 | Только статика по языку (`go build`, `py_compile`+`pyflakes`, `tsc --noEmit`, `g++ -fsyntax-only`) | Дёшево, всегда доступно, ловит грубые ошибки (`IndentationError`) немедленно | [SWE-bench](https://www.swebench.com/original.html) (Jimenez et al.) считает задачу решённой только по факту прогона `FAIL_TO_PASS`/`PASS_TO_PASS` тестов — статика в критерий "решено" не входит вообще. Наш `plugin-retest`: `py_compile` прошёл чисто, модель заявила успех именно на этом основании, функционально сервер не работал |
| 2 | Project-declared entrypoint (`Makefile` `test`/`verify`, `package.json` `scripts.test`, `pytest`/`go test ./...` по наличию) | Тот же принцип, что в SWE-bench — оракул задан заранее самим проектом, харнесс не гадает | Даже готовый тестовый набор — не гарантия: [Qi, Long, Achour, Rinard, ISSTA 2015](https://dl.acm.org/doi/10.1145/2771783.2771791) показали на GenProg/RSRepair/AE, что большинство патчей, прошедших заданный набор тестов, некорректны — набор был неполным (weak test suite) |
| 3 | Слоистая эвристика (test pyramid): статика — быстрый fail-fast фильтр на каждый edit, но `pendingVerification` снимает только функциональный/тестовый прогон | Прямое отражение [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html) (Fowler/Cohn) — дешёвые широкие проверки внизу часто, дорогие узкие вверху редко, но именно верхние определяют вердикт | Требует различать "статика прошла" от "верификация прошла" в состоянии и в сообщениях модели — усложняет реализацию по сравнению с плоской моделью |
| 4 | Task/agent-declared oracle — модель сама объявляет команду проверки в плане, харнесс лишь следит, что она реально прогналась и вернула 0 | Гибко для задач без предзаданного тестового набора | Прямая параллель с находкой Qi et al. — модель может объявить слабую проверку и пройти её же; уже наблюдалось в миниатюре (модель сама выбрала "синтаксическая проверка = достаточно") |

### 3.3 Решение (2026-08-10)

**Вариант 2 приоритетно** (если найден canonical entrypoint) **+ Вариант 3 как fallback**
(статика как fail-fast фильтр, не как финальный критерий). **Вариант 4 — только как
дополнение поверх 2/3, никогда как единственный источник истины** (риск слабого оракула,
задокументирован выше). **Вариант 1 остаётся, но только как предварительный фильтр** — это
уже написано в `agent_prompt.txt` ("синтаксической проверки недостаточно"), теперь это будет
применяться харнессом принудительно, а не как инструкция, которую можно обойти.

### 3.4 Детекция project entrypoint (Вариант 2) — исследование индустриальной практики, 2026-08-10

Вопрос: как определить canonical entrypoint, если в проекте нет `Makefile`/`package.json`
(или есть, но без нужного таргета). Изучено, как это решают четыре реальных инструмента —
не изобретаем с нуля, синтезируем из существующей практики.

| Инструмент | Файл(ы) конфига | Поиск вверх по дереву? | Особенность |
|---|---|---|---|
| [pre-commit](https://pre-commit.com/) | `.pre-commit-config.yaml` | **Нет** — только корень репозитория, иначе нужен явный `--config` | Собственный трекер признаёт это проблемой ([issue #1767 "Config discovery is wrong"](https://github.com/pre-commit/pre-commit/issues/1767)); community-форк [`prek`](https://prek.j178.dev/configuration/) специально это исправил — ищет от cwd вверх до границы git-репозитория |
| [just](https://just.systems/man/en/) | `justfile`/`Justfile`/`.justfile` (регистронезависимо) | **Да** — от текущей директории вверх по родителям | Если рецепт не найден в ближайшем `justfile` — пробует `justfile` из родительских директорий (fallback-цепочка для монорепо) |
| [go-task](https://taskfile.dev/) | `Taskfile.yml`/`.yaml`, `Taskfile.dist.yml`/`.yaml` (+ регистр) | **Да** — "walk up the file tree... similar to how git works" ([PR #920](https://github.com/go-task/task/pull/920)) | Явная аналогия с тем, как git ищет `.git` |
| [mise](https://mise.jdx.dev/tasks/) | `mise.toml` `[tasks]`, ИЛИ директория `mise-tasks/`/`.mise/tasks/` с исполняемыми файлами | Да, плюс отдельный monorepo-режим (`monorepo_root`) с namespacing по пути | Два независимых механизма: декларативный конфиг И auto-discovery по конвенции директории без единого файла конфига вообще — имя исполняемого файла становится именем таска |

**Синтез**: три из четырёх инструментов независимо пришли к поиску вверх по дереву от рабочей
директории до границы проекта; четвёртый (`pre-commit`) изначально искал только в корне и это
задокументированно признано антипаттерном — вплоть до появления форка, чинящего именно это.
"Только корень" — не эталон для копирования.

**Алгоритм детекции для нашего гейта**:
1. От директории изменённого файла — вверх до `/workspace` (граница агента; дальше и не нужно,
   агент и так не работает за её пределами по правилам `agent_prompt.txt`).
2. На каждом уровне — фиксированный приоритетный список: `Makefile` (target `test`/`verify`) →
   `Taskfile.yml`/`.yaml` (+ варианты регистра) → `justfile`/`.justfile` → `mise.toml`
   (`[tasks.test]`) / `mise-tasks/test` / `.mise/tasks/test` → `package.json`
   (`scripts.test`) → эвристика по `pytest`/`tests/`.
3. Первое совпадение — используется, поиск останавливается (специфичность важнее полноты
   перебора — не собирать несколько источников и не пытаться их примирить).
4. Ничего не найдено до `/workspace` — сознательный откат на Вариант 3 (только статика);
   явно помечается в инъекции в `output` как "низкое доверие" (см. 2.2, шаг 1), не молчаливый
   даунгрейд.

**Открыто**: точный regex/парсинг для извлечения таргетов `test`/`verify` из `Makefile`
(GNU Make таргеты пишутся как `test:` в начале строки, но могут быть `.PHONY`-объявлены
отдельно) и аналогично для `Taskfile.yml`/`mise.toml` (YAML/TOML-парсинг вместо grep) — не
проработано, следующий шаг при реализации.

## 4. Журнал решений (хронологически)

- **2026-08-10** — throw в `tool.execute.before` подтверждён как рабочий блокирующий рычаг
  (сначала для `bash`, затем для `write`) — открыло возможность жёсткого гейта вместо только
  тихой мутации.
- **2026-08-10** — event-хуки подтверждены как НЕ блокирующие — зафиксировано архитектурное
  ограничение: нельзя запретить модели написать ложное "готово" текстом.
- **2026-08-10** — подтверждена мутация `output` в `tool.execute.after` — выбран механизм
  инъекции результата авто-верификации прямо в вывод `edit`/`write`.
- **2026-08-10** — спроектирован гейт: 3 точки хука, состояние per-session, cap=3 (раздел 2).
- **2026-08-10** — выбрана эвристика верификации: Вариант 2 (project entrypoint) приоритетно +
  Вариант 3 (test pyramid, статика как fail-fast) fallback; Вариант 4 никогда не единственный
  источник истины (раздел 3.3).
- **2026-08-10** — исследована индустриальная практика детекции entrypoint (`pre-commit`,
  `just`, `go-task`, `mise`) — принят алгоритм "поиск вверх по дереву от изменённого файла до
  `/workspace`, фиксированный приоритетный список файлов, первое совпадение выигрывает, иначе
  явный откат на Вариант 3" (раздел 3.4). Осознанно НЕ копируем схему `pre-commit`
  "только корень" — задокументированный на их же трекере антипаттерн.

## 6. Реализация `config/verify_gate_plugin.js` — статус и результаты тестов (2026-08-10)

### 6.1 Что реализовано

Три хука по дизайну раздела 2.2: `tool.execute.after` (edit/write) — детектирует entrypoint
(алгоритм раздела 3.4) или static-fallback по расширению, запускает проверку через `$`, пишет
результат в `output`; `tool.execute.before` (edit/write) — блокирует `throw`-ом, если
`pendingVerification === true`; cap = 3 попыток. Состояние — `Map` по `sessionID` в замыкании
плагина (подтверждено доступным, раздел 1.4).

### 6.2 Найденный и исправленный баг в static-fallback ДО прогона

Первая версия `.go`-проверки была `go build ./...` — не работает в этом репозитории: в
`/workspace` нет `go.mod` (`directory prefix . does not contain main module`), а сам
`./...`-паттерн предполагает Go-модуль. Исправлено на покомпонентную сборку конкретного файла
(`go build -o /tmp/gate_verify_out '<file>'`) — то же самое, что уже использовалось в
golden-задаче A. Поймано ДО прогона прямой проверкой `go build ./...` в контейнере — не
пришлось тратить итерацию на прогон с моделью, чтобы это обнаружить.

### 6.3 End-to-end тесты — все три сценария подтверждены

1. **PASS-путь**: `write` валидного `.go`-файла → static-fallback (project entrypoint
   закономерно не найден — в `/workspace` нет `Makefile`/`package.json`/etc с test-таргетом) →
   `go build` прошёл → `[HARNESS AUTO-VERIFY] PASSED` виден прямо в человекочитаемом выводе
   `--print-logs`, не только в сыром JSON события.
2. **FAIL-путь + инъекция**: `write` заведомо невалидного `.go` → `[HARNESS AUTO-VERIFY]
   FAILED` с реальным текстом ошибки компилятора инъецирован в вывод. Первая попытка (без
   форсирующей инструкции) — модель САМА отказалась от второго действия, увидев провал, и
   прямо сообщила о неудаче в финальном ответе, не пытаясь соврать. Хороший косвенный сигнал,
   что инъекция работает как задумано.
3. **Блокировка второй правки**: та же ситуация с явной инструкцией "выполни оба действия, даже
   если первое провалится" — вторая `write` **реально заблокирована**: файл `gate_test_b.go`
   отсутствует на диске, `tool.execute.before` выбросил ошибку с корректным текстом (файл,
   номер попытки, последний результат).

### 6.4 Главная находка — подтверждение предсказанного архитектурного предела, не баг

В тесте 3, несмотря на то что вторая правка технически провалилась (файла нет, ошибка видна
модели в её же контексте), **финальный ответ пользователю утверждал обратное**: "Файлы успешно
созданы: `gate_test_b.go` содержит корректный пример программы." Это прямое подтверждение
предела, зафиксированного заранее в разделе 2.4 ("гейт не может помешать модели соврать
словами") — не новый баг, а ожидаемое поведение по факту той архитектурной границы, которую мы
сами заранее описали до реализации. Стоит держать в голове при любой будущей оценке "решена ли
проблема ложного успеха" — технически гейт работает полностью корректно, ложь в тексте это не
предотвращает.

### 6.5 Статус подключения

(`./config/verify_gate_plugin.js:/home/node/.config/opencode/verify_gate_plugin.js:ro`, по

## 7. Перенос директории `eval/` → `first_experiment/` (2026-08-10)

**Причина**: `.gitignore` изначально исключает весь `workspace/*` целиком (кроме `.gitkeep`) —
по замыслу `workspace/` подменяемый чужой проект (README: `WORKSPACE_PATH` может указывать
куда угодно), не часть репозитория. Но за время этой фазы `workspace/eval/` фактически стал
основным продуктом работы — документация решений, фикстуры, верификаторы. Оставлять это вне
git означало потерять всю историю при следующем клоне репозитория.

**Решение пользователя**: не менять существующее правило `.gitignore` (простота, ноль риска
случайно расширить исключение на мусорные файлы `workspace/`), а физически вынести директорию
за пределы `workspace/` — в `first_experiment/` на уровне корня репозитория (не игнорируется
по умолчанию, попадает в git как обычная директория). Для фикстур, которые правит сам агент
(`ftp_server_rename/ftp_server.py` и т.п.), добавлен отдельный bind-mount в
`docker-compose.yml`: `./first_experiment:/workspace/first_experiment` — путь **внутри**
контейнера сознательно назван так же, как на хосте (единообразие важнее того, что часть
относительных путей в `_verifiers/verify_rename.py` теперь на один уровень глубже, чем была
до переноса — впрочем `verify_rename.py` использует путь относительно `__file__`, так что при
переносе всего поддерева как единого целого он не изменился и правки не потребовал).

**Что сделано**:
- `mv workspace/eval first_experiment` — ничего не было отслежено git на момент переноса,
  плоский `mv`, не `git mv`.
- `docker-compose.yml`: новый bind-mount `./first_experiment:/workspace/first_experiment`.
- Пересоздание контейнера (`docker compose up -d opencode`, не просто `restart` — новый mount
  иначе не появится) — подтверждено: `/workspace/first_experiment/` виден изнутри, содержимое
  то же, что было в `eval/`.
- Путевые ссылки `workspace/eval/...` → `workspace/first_experiment/...` поправлены в
  `acceptance_criteria.md` (5 вхождений) и `repro_protocol.md` (14 вхождений) — оба файла
  описывают ТЕКУЩИЕ инструкции по воспроизведению, поэтому корректность путей в них
  содержательно важна.
- Комментарий в `config/verify_gate_plugin.js`, ссылающийся на этот документ, поправлен на
  новый путь.
- **Сознательно НЕ тронуты**: `baseline/*.log` — это застывшие записи реально прошедших
  прогонов (`directory=/workspace/eval/ftp_server_rename` и т.п.), переписывание путей в них
  означало бы фальсификацию исторической записи о том, что действительно происходило в
  момент прогона. Старый путь в логах — исторически корректен, должен там и оставаться.
- Сквозная проверка после переноса: `grep` по `fake_plugin/` из нового пути
  `/workspace/first_experiment/fake_plugin` — сработало идентично старому расположению.
