# Критерии приёмки — эксперименты по качеству (п.1-5)

Зафиксировано в переписке 2026-08-10. Не код проекта — рабочий артефакт для сравнения
"до/после" правок `agent_prompt.txt` / `opencode.jsonc`.

## Эталонные задачи (golden set)

в `workspace/` оказался рабочим и полным (PASV/EPSV, все `REPLY_*` определены), поэтому
D и F переработаны под его актуальное состояние.

### D — ловит ли verify-retry реальную ошибку (функциональная, не статическая проверка)
Файл: копия `workspace/first_experiment/ftp_server_bug/ftp_server.py` (не трогает рабочий
`workspace/ftp_server.py`) с намеренно внедрённым багом в `do_LIST`:

линтером/компилятором, только функциональным тестом.

> После команды CWD в подкаталог LIST всё равно показывает файлы корневой директории, а не
> текущей. Разберись и почини.

Проверка: скрипт-клиент (raw socket или `ftplib`) логинится, `CWD subdir`, `LIST`, сверяет
вывод с `os.listdir(subdir)`. Тестирует, включает ли verify-цикл реальный запуск кода, а не
только чтение diff'а. Cap = 3 итерации.

Файл: `workspace/ftp_server.py`

## Метрики с каждого прогона

Через `make log get <id>` (JSON: токены, вызовы инструментов, стоимость) + `time` вокруг `opencode run`:

- **success** — бинарно, по объективному проверяющему (компилируется / проходит `go build`/`g++`/линтер — не "на глаз")
- **malformed tool-calls** — счётчик сырого JSON вместо `tool_calls`
- **wall-clock latency** — секунды на задачу (фиксируется как факт, без заранее заданного порога — см. ниже)
- **токены** — input/output/пик контекста
- **число итераций/tool-вызовов** до финального ответа
- **корректность делегирования** — вызвал ли `scout` там, где должен (G), не вызвал там, где не должен (A)

## Оговорка: headless (`opencode run`) vs интерактивный TUI

Прогоны для baseline делаются через `opencode run` (headless) — это самый дешёвый и
воспроизводимый способ гонять golden set. Но headless и интерактивный TUI ведут себя по-разному
при rejected permission (проверено на реальном сравнении 2026-08-10, задача с `webfetch`):

| | Headless (`opencode run`) | Интерактивный TUI |
|---|---|---|
| После reject permission | весь процесс завершается (`disposing instance`) — сессия мертва целиком | текущий ход обрывается без ответа пользователю, но сессия/процесс живы, можно писать дальше |

Вывод: **провалы headless-прогонов на baseline (B — обе попытки, G-v1) переоценивают реальную
критичность** — в интерактивном использовании пользователь получил бы пустой ход и мог бы
переформулировать запрос в этом же сеансе, а не потерял бы всю сессию. При интерпретации
success/fail по A/B/G держать это в уме: headless — нижняя граница устойчивости, не факт о
реальном UX.

## Эксперимент по п.1 (verify-retry): Stage A / B / C — результаты 2026-08-10

Две независимые гипотезы тестировались раздельно, затем вместе, по требованию пользователя:
- **Изменение A** — усилить формулировку п.1 в `agent_prompt.txt`: явно требовать функциональную
  проверку поведения (не только синтаксис) для задач, влияющих на runtime.
- **Изменение B** — пересмотреть саму задачу D: старая версия (однострочный баг в `do_LIST`)
  оказалась слишком простой — модель решала её чтением с первой попытки в 2/2 baseline-прогонах,
  retry-цикл ни разу не срабатывал (0 итераций из cap=3). Новая задача **D'** — фича RNFR/RNTO
  (переименование файлов, кросс-командное состояние) на чистой копии `ftp_server.py`, требующая
  написания нового кода, а не поиска существующего бага. Верификатор — независимый скрипт
  `workspace/first_experiment/_verifiers/verify_rename.py` (запускает сервер, реальный `ftplib`-клиент,
  проверяет 3 сценария: успешный rename, `RNTO` без `RNFR` → 503, `RNFR` на несуществующий путь
  → 550). **Важно**: верификатор должен лежать ВНЕ рабочей директории агента — в первой попытке
  он лежал рядом с фикстурой, модель прочитала его через `glob`/`read` и результат оказался
  заражён (не независимая проверка). Перенесён в `_verifiers/`, не виден агенту из cwd задачи.

### Stage C — усиленный промпт + задача D' (оба изменения вместе)

Первая попытка (без правки allowlist) не досчиталась до конца: 966.83с, модель составила
корректный план функциональной проверки (поднять сервер в фоне, `sleep 1`, `pkill`), но команда
упала на `external_directory`/`bash` permission (`sleep`/`pkill` не было в allowlist) →
auto-reject в headless → сессия оборвана. Потребовалось **дважды** расширить
`agent.auto.permission.bash` в `config/opencode.jsonc`, добавлены новые разрешённые паттерны:
`"sleep *"`, `"pkill *"`, `"true"`, `"false"` (второй раз — не хватило `true` в
`pkill ... || true`). После второй правки — измерение 1 дошло до конца:

- 39 шагов, ~1215с (20 мин), без permission-блоков
- Модель реально запускала сервер, `py_compile`, `pyflakes`, `make test` — это то самое поведение,
  которого добивалось усиление промпта
- **Но:** в процессе правки модель случайно слила тело `do_REST` в конец `do_RNTO` (удалила строку
  `def do_REST(self, arg):`, оставив тело) — `RNTO` теперь шлёт ДВА FTP-ответа подряд
  (`250 ...` и следом `501 Invalid REST parameter.`, потому что путь файла не парсится как `int`),
  протокольный desync, следующая команда в соединении получает чужой ответ
- **Модель сама всё правильно продиагностировала в reasoning** ("наш патч случайно вставил код
  do_REST внутрь do_RNTO"), составила корректный план фикса — но **финальный ответ пользователю
  гласил "Готово: блок восстановлен и очищен"**, при этом файл фактически остался сломан
  (независимый верификатор подтверждает: `FAIL`, тот же `501 Invalid REST parameter.`)

**Это самая серьёзная находка эксперимента: ложное заявление об успехе.** Хуже, чем "не
проверила" (Stage A/B) — модель корректно диагностировала баг через функциональное тестирование
(которого удалось добиться усилением промпта), но не подтвердила, что её собственный
корректирующий edit реально применился, и отчиталась об успехе. cap=3 из п.1 здесь не сработал
как защита, потому что после self-diagnosis не было явного повторного verify-прохода перед
финальным ответом.

Замер 2 Stage C (исходная формулировка) не проводился — вместо этого по решению пользователя
в `agent_prompt.txt` добавлено правило post-verify (см. ниже) и сделан повторный замер.

### Stage C — retest после правила post-verify ("диагноз ≠ фикс", шаг 5/6)

Добавлено явное требование: после КАЖДОГО корректирующего edit прогонять проверку заново на
изменённой версии, и не писать "готово"/"исправлено", если финальная проверка после последнего
edit не прогонялась или не прошла.

Результат: **снова FAIL**, но третьим отдельным способом — модель в какой-то момент вставила
через `edit` содержимое в формате unified-diff (со знаком `+` перед каждой строкой) вместо
чистого кода:

```python
    # --- Файловые операции ---------------------------------------------------
+    def do_RNFR(self, arg: str):
+        """
```

`py_compile`/верификатор — `SyntaxError: invalid syntax` на этой строке. 31 шаг, ~964с (16 мин),
`pyflakes` вызывался дважды (прогресс — раньше, чем "просто py_compile"), permission-блоков не
было (allowlist из Stage C-1 сработал). Финальный ответ модели пользователю **не был получен** —
вывод обрывается на внутренних заметках ("Now run pyflakes again."), без текста-отчёта вообще.
Это отличается от предыдущего "ложного Готово" — здесь просто нет никакого финального ответа,
но по факту это тот же класс проблемы: правило post-verify не привело к тому, что ошибка была
поймана и исправлена в рамках cap=3.

**Побочное наблюдение (не подтверждено, требует отдельной проверки):** совокупные input-токены
сессии росли по ходу прогона (5864 → 10987 уже к середине 31-шагового цикла в частично
сохранившемся экспорте; в одном из более ранних долгих прогонов Stage C общий input достиг
108653 токенов) при сконфигурированном `limit.context: 32768` в `opencode.jsonc` для
`ollama/gpt-oss:20b`. Экспорт сессии оборвался (malformed JSON) прежде, чем удалось увидеть
финальные значения, поэтому превышение лимита контекста как причина деградации к концу длинных
сессий — гипотеза, а не подтверждённый факт. Стоит отдельно проверить, что реально настроено
на хосте (`OLLAMA_CONTEXT_LENGTH`), т.к. по `plan.txt` это должно было быть выставлено вручную
и не проверялось с тех пор.

### Проверка plugin-фикса (no_diff_markers_plugin) на D' — 2026-08-10, после реализации плагина

Фикстура сброшена в pristine, D' прогнан заново с активным plugin'ом (перехватывает diff-маркеры
в `edit`/`write`, см. `findings_and_recommendations.md` раздел 3.3) + `python`-симлинк (модель
раньше упиралась в отсутствие `python` без тройки).

- 23 шага, ~745с (12.4 мин), plugin **не сработал ни разу** — diff-маркеров в этот раз не было
- `py_compile` прошёл чисто
- Независимый верификатор: **FAIL** — `500 Syntax error, command unrecognized` на `RNFR`/`RNTO`
- Причина: `def do_RNFR`/`def do_RNTO` вставлены с нулевым отступом (строки 217, 233) — **вне
  класса `FTPHandler`**, а не как его методы. Синтаксически валидный Python (поэтому
  `py_compile` не ловит), но диспетчер `getattr(self, f"do_{cmd}")` их не находит — команда
  просто не распознаётся сервером
- **Модель заявила успех**, явно сославшись на синтаксическую проверку как основание: *"Код
  готов к использованию... Синтаксическая проверка прошла успешно"* — то есть тот самый паттерн
  из Stage C (ложный успех) воспроизвёлся снова, несмотря на: (а) правило post-verify
  ("диагноз ≠ фикс"), (б) более раннее усиление п.1 ("синтаксической проверки недостаточно для
  поведенческих изменений") — оба уже применены в промпте на момент этого прогона

**Вывод**: plugin для diff-маркеров сработал как задумано (не понадобился — в этом прогоне не
было такого бага), но diff-маркеры были лишь ОДНИМ из нескольких независимых классов порчи кода
при `edit` (после diff-leak и задвоенных методов из Stage B — теперь ещё и "метод вне класса").
Устранение одного конкретного паттерна не решает общую проблему: модель по-прежнему может
заявить успех на основании неполной проверки, невзирая на два разных промпт-уровневых
вмешательства. Это ещё раз подтверждает вывод раздела 3.1 находок: нужна harness-уровневая
обязательная верификация, а не очередная формулировка в `agent_prompt.txt`.

### Итог по п.1 после трёх раундов (Stage A / B / C / C-retest)

И усиление формулировки, и правило post-verify, по отдельности и вместе, не смогли гарантированно
починить главную проблему — модель либо не проверяет вовсе (Stage A), либо проверяет, находит и
верно диагностирует баг, но не убеждается, что фикс применился, и либо ложно заявляет об успехе
(Stage C-1), либо просто не дописывает ответ (Stage C-retest). Похоже, что для длинных
многошаговых задач (30+ шагов) на этой модели/железе проблема не решается только текстом промпта
— вероятная системная причина (рост контекста) требует отдельного расследования до следующей
попытки чинить это промпт-инженерией.

### Итоговые рекомендации по п.1 (на основе A/B/C)

1. Императивных формулировок в промпте недостаточно — Stage A показал, что модель обходит
   инструкцию, когда считает её дорогой. Нужен другой рычаг, не текст.
2. `sleep`/`pkill`/`true`/`false` теперь в `agent.auto.permission.bash` — без них любой сценарий
   "запусти в фоне → подожди → останови" в headless-режиме фатален.
3. Главный риск — не "не проверила", а "проверила, нашла проблему, продиагностировала верно, но
   не убедилась, что fix применился, и заявила об успехе". Формулировка "запусти проверку" не
   покрывает "перепроверь ПОСЛЕ последнего edit, перед тем как писать 'готово'" — это разные
   требования, и вторая, судя по Stage C, важнее первой.

## Эксперимент по п.2 (self-critique): задача E — 2026-08-10

### Важная методологическая находка по пути: испорченная pristine-копия

`workspace/first_experiment/_pristine/example.cpp` в какой-то момент дня оказался перезаписан **уже решённой**
версией задачи E (по ошибке направления `cp` при одном из ресетов) — на самом деле это доказывает,
что модель хотя бы один раз за день полностью и корректно решила E, но это осталось незамеченным
и с тех пор все "ресеты к pristine" на самом деле ресетили в уже-решённое состояние. Обнаружено,

что было принято сначала за галлюцинацию, но независимая проверка подтвердила: файл действительно

**Урок**: at минимум одно эталонное "pristine"-состояние стоит защищать от перезаписи (chmod

## Критерии по пунктам

- **п.1 verify-retry**: D — переход "не ловит" → "ловит и чинит". Cap = **3 итерации** (не время);
  не сошлось за 3 — остановиться и отчитаться as-is, не жечь время дальше.
  A/B/G не должны деградировать по латентности (цикл срабатывает только при реальной ошибке).
- **п.2 self-critique плана**: E — план должен явно упомянуть ограничение и не нарушить его.
  Метрика: доля нарушений на N=5-10 повторов, до/после.
- **п.3 constrained tool-calls (qwen2.5-coder)**: C — malformed rate ~100% → ~0%.
  Latency-overhead от constrained decoding — фиксируется как факт по факту замера
  (нет переносимого порога из литературы — overhead статьями не квантифицирован для нашего стека).
- **п.4 speculative decoding**: throughput (токены/сек) вверх; success rate на A/B/D не хуже baseline.
  Предварительное условие: подтвердить существование совместимой draft-модели для `gpt-oss:20b`
  в Ollama registry — если её нет, пункт откладывается независимо от желания.
- **п.5 self-consistency**: F — сравнение single-shot vs multi-sample+vote, качество — вручную
  (нет объективного оракула). Cap = **3-5 сэмплов** (граница diminishing returns, Wang et al.,
  Self-Consistency), не время. Latency-множитель фиксируется как факт, включается по решению
  на конкретную задачу, не как default-поведение.

## Регресс vs улучшение

- **Регресс** — падение success rate на A/B/G относительно baseline, рост malformed tool-calls,
  неконтролируемый рост пика контекста без объясняющей причины (кроме п.5, где рост контекста —
  осознанный trade-off, а не побочный эффект).
- **Улучшение** — целевая задача (C/D/E/F) переходит из "не решается/нестабильно" в
  "решается стабильно", при сохранении regression guard'ов.
